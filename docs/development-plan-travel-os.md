# China Travel Agent · Travel OS 开发计划

版本：2026-09-27。状态：M0 最小契约与 M1 一日样板代码已实施；真实高德联调、现场与真机验收待完成。详见 progress-2026-09-27.md。
工作目录：`/Users/xianli/codex/china-unfold`。

## 1. 本阶段目标与范围

为第一次或前几次来中国的外国游客，提供视觉化、可执行、可离线使用的旅行工具。衡量标准是用户能否找到正确入口、理解预约要求、到达正确车站、看懂每日安排，并在断网时继续使用。

本轮交付：北京、上海、西安三个深度城市指南；China Travel Cards；一份编辑审核的 10-Day First Trip to China 样本；以相同数据生成、可修改的 My China Journey；完成收费前必需的交付保障。

优先级：私人旅行册 > 可离线的旅行卡 > 三城网站深度内容 > 完整中国指南商品化。保留已有 42 城 URL 与基础浏览，不扩城，不把未审核城市包装成同等深度。首版以英文解释 + 中文地点/菜名为主；内容模型支持后续本地化。原生 iOS、十种完整语言、旅游交易撮合不进入本阶段。

## 2. 现状与复用边界

当前代码已经有 42 城 × 8 个景点或区域、食物/住宿/交通/路线介绍、图片许可记录、搜索收藏、规则行程生成、PDF 导出，以及默认关闭的 Stripe 支付入口。

仍缺少：稳定的地点 ID、入口级位置、字段级来源与核验日期、中文行动卡、真正的地图/动线、按时间和预约约束编排的日程、离线资源包、可恢复的订单权益。

保留 Next.js、已有 URL、真实照片和许可档案、收藏与支付框架。逐步替换以英文名称匹配景点、依赖文字关键词判断远近、用直线距离判断交通、把同一套介绍排成长 PDF 的实现。旧 42 城数据经适配器继续工作，不伪造缺失的精确信息。

## 3. 三层产品边界

| 层级 | 用户获得的价值 | 首轮交付 |
| --- | --- | --- |
| 免费网站 | 搜索发现、选城市与区域、判断节奏、建立信任 | 三城完整指南；示范卡可直接使用；真实旅行册内页预览 |
| Complete China Guide | 系统准备知识、跨城市比较、离线工具箱 | 先建立四部分目录和三城样章，不立即销售尚未核验的 42 城全集 |
| My China Journey | 与本人日期、同行人、预算和偏好匹配的执行方案 | 三城范围内的可编辑计划、预检、私人旅行册与离线卡片包 |

免费层不故意隐藏关键入场条件和安全信息。付费价值来自经过组织的个人日程、集中准备事项、预算、衔接方案和离线交付，而不是把网页打印出来。价格先不写死，待真实样本的购买测试后决定。

多语言架构另见 [多语言架构方案](multilingual-architecture.md)：内容事实、译文、界面消息与模板分层；先通过北京 Daybook 英文+韩文验证，再扩展语言与城市。

## 4. 按依赖推进的里程碑

### M0 — 产品契约与内容模型（P0）

- 冻结三城范围、英文 + 中文卡片策略、免费/付费边界、首次旅行目标用户。
- 设计 City、Place、Entrance、TransportHub、Transfer、Route、TravelCard、Trip、DayPlan、Source、Asset、BookDocument 数据结构。
- 每条实体使用稳定 ID；中文名、英文名、别名分开存储；入口与景点主体分开；住宿区域与用户实际酒店分开。
- 建立事实状态：已核验、待核验、无法确认、已过期；区分官方事实、编辑建议、预算估算、用户已确认订单。
- 完成设计 token 和四类组件规格：摄影、地图、路线动线、信息卡。网站和 PDF 分别排版，共享内容和视觉规则。

交付：数据字典、样例数据、迁移适配方案、组件清单、验收清单。
验收：同一地点可在城市页、卡片和 PDF 中被稳定引用；缺失字段不会被自动补成看似真实的地址或时间。

### M1 — 北京一日完整样板（P0，首个实现任务）

用“故宫 → 景山”作为一条有代表性的路线；进入方式、预约要求、步行衔接以实际核验为准。

- 网页：入口说明、实景图、地图、参观方向、摄影建议、预约准备与替代方案。
- Travel Card：中英文名、经核验的中文地址、入口导航词、司机短句、地铁站/出口（已核验才展示）、备注、来源日期。
- 地图：区分司机可达下车点、步行进入点、景区正式入口；地图上的景点坐标不直接等于可停车入口。
- 交互：复制中文、保存为图片、加入行程、移除、查看已保存卡片。
- 离线：已下载图片卡、PDF 必须无网络可读；在线导航链接清楚标注需联网。
- PDF：做出开篇、日程、景点执行页、交通页、中文卡、Plan B 六种代表性版式。复杂一天允许跨页，不为了“一天一页”压缩至不可读。

验收：在手机断网状态下，测试者可以找到正确入口、展示中文卡、理解游览顺序与待预约事项；同一事实在三种输出中一致。该样板通过前，不批量生产三城所有精细卡片。

### M2 — 三城编辑内容与旅行卡（P0）

每城目标（以内容必要性调整，不为凑数填充）：

- 10–12 个优先体验，共约 30–36 个，全部具有可执行字段；确有价值时再扩至 15 个。
- 3–4 个住宿区域，说明适合谁、交通代价、优缺点；不虚构酒店评价。
- 6–8 种食物，提供中文名、口味/常见原料、点餐方法和适合寻找的街区；配方差异明确说明。
- 12 个月的体验说明、气候与人流提示；这是季节资料，不是未来天气预报。
- 1/2/3/4 天的取舍与停留建议，1–3 日路线模板。
- 首次到访准备：支付、实名信息、预约、入场证件、交通枢纽辨别。
- 每个核心景点至少一张主题准确且许可可用的实景图；城市概览图、住宿区图、路线图各司其职。
- 景点卡、实际涉及的机场/车站卡、餐饮卡、酒店地址占位卡与通用工具卡。酒店未指定时不生成虚构酒店地址。

内容工作流：选题 → 官方或运营方资料 → 事实录入 → 编辑建议 → 中文专名复核 → 图片/地图许可检查 → 网页与 PDF 样章审阅 → 发布。二手攻略用作线索和补充，不作为所有动态规则的唯一依据。

验收：三城关键执行字段均有来源和核验日期；核心入口信息存在未解决冲突时，该执行卡不可作为“已准备好”导出。不能用统一免责声明代替逐项状态。

### M3 — 10 天编辑样本与 PDF 系统（P0）

先做编辑确定的基准行程，再要求生成器达到这个质量，避免拿自动生成的错误作为产品模板。

建议基准：北京 → 西安 → 上海；2 名成人、中等节奏、历史与美食。选定实际日期后核验开放日与预约安排。

| 日期位置 | 计划角色 |
| --- | --- |
| Day 1 | 抵达北京、入住、轻量活动；依到达时间调整 |
| Day 2–3 | 北京核心体验；其中一个专程游览日 |
| Day 4 | 北京 → 西安，预留完整交通衔接与入住 |
| Day 5–6 | 西安市内与兵马俑专程游览 |
| Day 7 | 西安 → 上海，预留交通与入住；交通方式经比较后确定 |
| Day 8–9 | 上海街区、博物馆与河岸体验 |
| Day 10 | 按离境时间安排，不默认拥有完整游览日 |

旅行册包含：个人封面、旅程总览、准备清单、预约时间线、每日时间段与节奏、概览地图、每日路线、图片、中文卡、餐饮区域与菜名、行李安排、预算区间与假设、天气/售罄 Plan B、来源与版本信息。预期约 30–45 页，以可读性为准，不以页数作为卖点。

时刻分三种：编辑建议的活动时间段、交通耗时估算区间、用户已确认的真实班次。没有出票或可靠数据时，不生成 G87、09:15 等仿真的车次和时刻；用“待选择班次”及可行窗口表达。预算显示币种、人数、包含项、估算日期；外币换算需说明汇率来源与日期。

Complete China Guide 同期只建立版式骨架：Before China → Plan Your Trip → Destinations → Travel Toolkit。私人旅行册的目录与内容按用户旅程裁剪，不复制整本中国指南。

验收：样本十天连续可读，抵达/离开/转城时间有缓冲；未确认事项集中可见；离线有中文、地图、动线、图片和备用方案；字体嵌入、目录链接、页码、版权信息、手机阅读均通过实际渲染检查。

### M4 — 私人旅行册生成与编辑（P1）

在样本验证后升级生成器，首先仅支持三个样板城市的可执行旅行册。

- 新输入：到达/离开城市与时间（允许未知）、预算币种和是否包含国际交通、同行年龄与行动需求、酒店/区域、节奏、已订交通和预约、饮食偏好。
- 用户可以调城市顺序、替换景点、锁定已订项目；修改后重新计算受影响的日期与衔接。
- 确定性规则负责：开放日、时段、游览时长、预约冲突、路程缓冲、交通日、体力、预算汇总、重复点与选中点遗漏。
- 路线先从编辑批准的组合模板生成；交通边保存方式、起终点、耗时区间和依据，不能把直线距离直接换成可执行时长。
- AI 负责理解偏好、解释取舍和在已审核候选中提出选择；不拥有地址、价格、营业规则和班次的事实生成权。调用失败时仍能生成模板方案。
- 不可行请求给出原因和少量调整选项；不静默删掉用户必去项目。
- 每次生成有 ID、版本和内容快照。记录用户输入、采用的内容版本、确认状态、生成状态，支持重试与恢复；重新生成不得悄悄覆盖已下载的版本。

验收：正常、紧张、预约失败、输入信息不足、多人慢节奏、预算过低等用例均有可解释输出。对已确认车次和预约保持不变；任意替换后重跑预检。示例中的约 12 天/4 城请求如果无法舒适实现，必须明确取舍。

### M5 — 网站入口、离线与转化（P1）

- 首页使用“CHINA / UNFOLD”“See China clearly. Travel it confidently.”与真实摄影，提供按感受探索、首访路线、卡片演示、私人旅行册真实预览。
- 城市页补全 Why go / Best time / How many days / Where to stay / Experiences / Food / Getting around / Before you go / Chinese cards / Routes。
- 保持主要指南内容可被搜索引擎读取：服务端内容、稳定 URL、标题与摘要、站内链接、站点地图；不因重设计破坏已有 42 城路径。
- 增加“我的旅程”：收藏地点 → 查看卡片 → 加入日期 → 预检 → 预览 → 下载。
- 离线分两级：先完成下载到手机的图片卡与 PDF；随后实现网页离线包，显示下载进度、大小、完成状态、版本及更新入口。浏览器缓存可能被清除，不能将其描述为永久保存。
- 保存/分享按平台能力提供降级：支持时使用系统分享，否则下载图片或提示截图；验证真实 iPhone Safari 后才承诺相册保存体验。
- 本地离线包不默认存付款信息、护照号或不必要的私人资料；提供删除入口。

验收：新用户能从城市页进入一次完整的个性化预览；已下载内容在飞行模式下可读。在线地图失效时，静态图和中文位置仍可使用。

### M6 — 用户验证与付费交付（P1，销售门槛）

先邀请 5–8 名符合目标人群的测试者，使用真实样本完成“找入口、辨车站、改路线、看待预约、断网找卡片”任务。记录耗时、错误与理解偏差；这轮小样本用于发现问题，不足以证明市场成立。

商业验证围绕 My China Journey：记录预览到下载、主动查看购买入口、真实购买与退款反馈。价格和是否愿意付费不能仅靠口头评价确定；测试任务指标和购买指标分开。目标：关键任务至少 80% 测试者无需帮助完成，零个已知的错误入口/车站等严重事实错误；这是初始内部门槛，可按观察调整。

收费上线前补齐：持久化订单与权益、签名 webhook 校验与幂等处理、生成任务重试、跨设备恢复下载、签名下载地址、购买与生成失败的状态协调、退款与权益撤销、可联系的支持入口、实际商品范围与更新政策。测试支付成功、取消、重复通知、生成失败、超时、退款和重发下载。密钥齐全不等于具备上线条件。

首批销售范围必须清楚注明仅支持已完成核验的三个城市。42 城完整指南另行经过相同内容验收后推出。

## 5. 核心数据模型

| 对象 | 关键字段/约束 |
| --- | --- |
| City | 稳定 ID、双语名称、区域、12 月资料、停留方案、住宿区、体验/食物/路线引用、发布级别 |
| Place / Entrance | 地点与入口分别建 ID；中文导航词、地址、入口说明、可达下车点、坐标及坐标系、地铁信息、图像引用 |
| VerifiedFact | 值、来源 URL、来源类型、核验日期、适用日期/条件、状态、复核到期日期；可保留冲突记录 |
| VisitRule | 时长建议与依据、开放日/临时例外、预约渠道与窗口、证件规则、购票状态；未知不等于无需预约 |
| Transfer | 起终入口或枢纽 ID、方式、耗时范围、换乘/安检/行李缓冲、费用估算、来源、确认状态 |
| TravelCard | 卡类型、所引用事实、英文解释、中文展示句、离线资源清单、版本；不维护重复地址文本 |
| DayPlan / Stop | 日期、地点 ID、建议时间窗、前后交通、预算、预约状态、行李、替代项目、用户锁定状态 |
| Trip | 旅客参数、日期与国际到离信息、城市、实际酒店（可空）、锁定订单引用、方案版本、预检结果 |
| BookDocument | 内容快照版本、章节/页面块、卡片与资源引用、目录与跳转；网站与 PDF 使用不同布局 |
| Asset / Map | 拍摄对象、作者、许可、来源、替代文字、裁切焦点；地图提供方、许可、坐标系、数据时间 |

地图必须区分 WGS84 / GCJ-02 等坐标体系；网页导航链接与印刷静态图分别校验。离线地图采用允许静态/离线使用的素材或自制示意图，不随意抓取第三方地图瓦片。步行线路示意、精确导航、估计时间在呈现上明确区分。

## 6. 代码实施切分（原建议；实际实现见进度文档）

- `src/lib/content/`：类型、校验器、来源与内容状态、旧数据适配器。
- `src/content/cities/`、`places/`、`routes/`、`toolkit/`：按稳定 ID 分文件的编辑数据。
- `src/lib/planning/`：输入规范化、路线模板、约束预检、费用、版本与 AI 辅助接口。
- `src/lib/book/`：旅行册文档模型、页面模板、版面测量与输出。
- `src/components/travel-cards/`、`maps/`、`journey/`：共享展示组件。
- `src/lib/offline/`：资源清单、下载状态、版本和删除。
- `docs/editorial/`：三城研究、事实审阅、引用、图片与地图许可记录。

第一阶段继续使用可版本管理的本地内容文件，不先搭建大型 CMS。持久化存储从行程版本、生成任务、订单权益的实际需求引入。PDF 首先对现有 pdf-lib 做六种版式的技术验证；只有排版/分页/维护成本无法满足样板时才迁移渲染方式。不要同时重写前端、数据库、PDF 与原生 App。

## 7. 排期、发布与回退

采用里程碑交付，不把未经研究的内容生产量换算成确定日期。建议工作顺序：

1. M0 + M1：一个真实可用的一日闭环。
2. M2 与 M3 迭代：先北京，其次西安、上海；完成十天编辑样本。
3. M4 + M5：生成器追上样本质量，完成网站与离线交付。
4. M6：可用性验证、真实购买验证、限范围收费。
5. 验证通过后：按相同内容门槛扩城，再评估原生 iOS 与语言优先级。

第一阶段完成后，用实际的一日样板制作成本估算其余内容。关键路径通常是官方信息核验、可用实景素材、地图许可和中文校对，不只是页面编码。每阶段可以独立演示；未达到门槛时继续保留现有网站和免费预览，不把所有访客切换到未完成流程。
