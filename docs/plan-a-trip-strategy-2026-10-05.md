# Plan a Trip：方案设计、现状与下一步

> 更新：2026-10-05。范围仅为 `china-unfold` 的 `/[locale]/plan` 对话式行程规划工作台；`?view=classic` 是保留的旧版参考入口，不计入新方案的完成度。本文按当前代码与现有项目文档整理，页面能力和数据真实性分别评估。

## 1. 产品目标

为第一次或不熟悉中国的外国游客，把泛泛的目的地建议变成**与本人日期、酒店、同行者、已订车票和门票相关的可执行安排**。用户应能先探索，再用自然语言制定和反复修改行程；每次调整后，地图、每日时间线与待确认事项同步变化。

核心价值不是“列出上海景点”，而是回答：住在这家酒店、带父母、已有 10:00 的预约，哪天去哪儿、怎样抵达正确入口、路上和排队要留多少时间、哪些事情仍须自己确认。

### 设计原则

1. **对话优先**：不要求用户通过一串下拉框预先完成所有选择。信息不足时先给谨慎草案，再问最影响可行性的少量问题。
2. **地图与日程是同一个计划**：整趟旅程和单日都可查看；地点、交通线、选择状态与对话修改保持一致。
3. **事实有出处和状态**：区分用户确认的订单、官方规则、高德匹配地点与交通估时、联网搜索线索、模型建议。无法确认的内容不能包装成已核实事实。
4. **为外国游客设计执行层**：界面和解释用英语；导航时保留可复制的中文专名。景点中心点、正式入口、出租车下车点和车站不能混为一个坐标。
5. **可调整且能解释取舍**：保留已订项目；遇到冲突说明原因并提出替代方案，而不是悄悄删掉必去地点。

## 2. 目标交互与技术流程

```text
用户自然语言提问
    ↓ 问题分类
旅行助手：景点、餐饮和交通等咨询 → 联网检索/适用时查询高德 → 回答，不修改行程
路线管家：创建或修改行程 → Qwen 强制联网检索 → 结构化草案
                                   → 高德地点匹配、路线估时、可用天气预报
                                   → 时间与预约冲突检查 → 行程、地图、待确认清单
非旅行问题：友好说明服务范围
```

路线管家的输出应分三层展示：**建议安排**（为什么这样排）、**核验结果**（地点、交通、天气、来源与查询时间）、**行动事项**（预约、入口、车次、排队和其他仍待确认的信息）。浏览搜索结果本身不等于验证了某条开放规则。

## 3. 已完成的功能

| 领域 | 当前实现 | 仍需注意 |
| --- | --- | --- |
| 对话分流 | 每条新问题先由模型分类；路线调整交给 Route Concierge，旅行知识咨询交给 Travel Assistant，非旅行问题给出友好答复。咨询后可继续要求把选中的地点加入行程。 | 分类依赖模型调用；需要持续用真实语料检查误分流。 |
| 联网规划 | 每次创建或修改行程先调用 Qwen 联网搜索，保留摘要与来源；搜索无可用结果时返回可重试错误，再由模型生成结构化草案。 | 来源质量和新鲜度不一致；页面展示来源不代表逐条事实已核实。 |
| 自然语言约束 | 支持日期、城市、酒店、同行者、节奏和已预约项目；普通修改会保留旧计划中的固定预约时间。 | 当前草案上限为 **10 天、每天 4 个主要停留点**；复杂长线旅行需扩展分段规划。 |
| 高德核验 | 用高德 Web Service 匹配酒店与景点，查询步行/驾车/公交等路线估时、路线几何和可用日期的天气；对未匹配地点、无路线或无预报标记待确认。餐厅咨询已有“酒店附近餐饮”专门查询路径。 | 高德地点名称和地址常为中文；路程是查询时估值，不能当作未来准点承诺。英文 POI 查询因当前权限不足而不依赖该能力。 |
| 时间与跨城 | 按景点停留、路程和缓冲编排时间，检查固定预约冲突与过晚结束；跨城日计算起终点估时并显示规划缓冲。 | 跨城日目前采用 **08:00 出发、额外 45 分钟缓冲**的假设；未核实实际车次、机场/车站、余票、安检和行李时间。 |
| 地图 | 桌面左侧地图、右侧独立滚动的对话与日程；移动端切换视图。可看 Whole trip 或单日，缩放、拖动、适配全部点、选中标记；有高德路线几何时用实线，其余连接用虚线。 | 高德英文 JS 底图需要多语言地图权限；2026-10-07 起，未开通时使用高德中文底图，地点、路线、天气同样来自高德，坐标直接叠加。权限开通后通过英文地图开关切换语言。虚线只表示示意连接。 |
| 景点与照片 | 地图下方有景点介绍、与本次旅行相关的理由、提示、地址/交通信息和照片；优先取高德 POI 图片，缺图时以已标注的城市配图或缺图状态兜底。 | 城市配图不是该景点实景；照片覆盖、适用性与许可仍需逐张核对。英文展示依赖模型输出和本地名称转换，旧存档仍可能有中文回退提示。 |
| 保存与修改 | 对话及最新计划保存在当前浏览器 `localStorage`；支持新行程和撤销上一次成功修改。 | 目前没有用于这套对话规划的后端行程数据库，也没有账号同步、跨设备恢复、共享协作或完整版本历史。 |
| 边界提示 | 页面显示联网来源、天气状态、未核实路段与“出行前确认”清单；缺失模型或高德配置会报错。 | “已匹配高德地点”不等于正式入口、营业时间或预约政策得到官方确认。 |

**关键实现位置**：`src/app/[locale]/plan/page.tsx`、`src/components/travel/Planner.tsx`、`src/components/travel/ConciergeJourneyMap.tsx`、`src/lib/travel/concierge.ts`、`src/lib/travel/concierge-amap.ts`、`src/app/api/trip-concierge/route.ts`。现有实现说明见 [`plan-a-trip-workbench.md`](plan-a-trip-workbench.md)。

## 4. 数据来源与可信度约定

| 数据 | 当前/计划来源 | 页面应如何表述 |
| --- | --- | --- |
| 景点、酒店、餐厅坐标与路程 | 高德 POI、路线 API | “地图匹配”与“查询时估算”，保留中文导航名、查询时间；匹配错误可纠正。 |
| 景点背景、季节和旅行建议 | Qwen 联网检索及模型整理 | 给出可点击来源；区分官方来源和一般网页，遇冲突写明不确定。 |
| 预约、入口、开放日、证件、票价 | 优先景区/运营方官方渠道 | 未逐条核实时显示“待确认”，不以高德 POI 营业字段或模型语句直接定论。 |
| 天气 | 高德可用日期预报 | 写明预报发布时间；超出预报范围不生成“当天的天气”。 |
| 景区拥挤程度 | **尚未接入**。可优先收集景区/文旅部门逐月客流或开放的饱和指数，辅以节假日、周末、预约余量等信号。 | 明确区分“历史月度趋势”“指定日期的预测”和“实时客流”；缺可靠数据时不显示伪精确数值。高德热力图只是数据展示工具，不直接提供逐月客流。 |

数据进入规划前应记录 `source`、`checkedAt`、`validFor` 和 `status`（已核验/估计/待确认/过期），并让前端能够查看。Qwen 用来搜索、归纳和解释；高德用于地理匹配与路线；两者都不能凭空确认门票或班次。

## 5. 下一步：按价值和依赖排序

### P0 — 让一条真实路线可执行

1. **完成景点与入口的事实模型**：为北京、上海、西安的高频景点分别记录英文名、中文导航名、景区坐标、正式入口、可到达下车点、开放/预约规则、来源和复核日期。先做好少量高价值景点，不把旧有城市简介自动当作执行资料。
2. **升级行程预检**：把开放日、入场时间窗、已订票时间、移动能力、午餐/休息、排队与跨城门到门缓冲放进明确的约束检查。发现不可能的安排时给出可操作的替换方案。
3. **核实跨城方案**：比较高铁/飞机/驾车等适用方案，明确车站或机场、接驳、检票/安检、行李和酒店入住时间。没有可验证的班次和余票时只给可行时间窗，不编造车次。
4. **补齐英文执行卡**：游客阅读英文解释，同时能复制中文地点、入口和给司机看的目的地；避免页面上的原始中文地址成为唯一可读信息。

**验收**：以“住上海指定酒店、带父母、首日 10:00 已预约豫园”的真实任务为例，用户无需自行猜入口、衔接方式和哪些信息必须重新确认；一次修改后地图、时间线、预约和待办保持一致。

### P1 — 做出通用聊天工具难以替代的旅行能力

5. **拥挤与季节决策**：试点景点显示 12 个月历史客流趋势；选定日期后叠加工作日/周末、节假日、预约余量和天气，给出有依据的拥挤风险与更合适的游览时段。先审计来源覆盖率，再决定哪些景点可以展示数值，哪些只能给定性提醒。
6. **持久化与版本**：引入后端行程、来源快照和版本记录；支持跨设备恢复、比较/撤销多次修改、分享只读行程。当前浏览器存档应可迁移，私人资料遵循最小化保存。
7. **行前再核验**：临近出发自动或按需重新查询天气、道路和官方预约/开放信息，标出与原计划不同的部分，让用户选择是否调整；不得静默覆盖固定订单。
8. **离线交付**：导出与当前计划同版的行程册及中文地点卡，包含待确认清单、来源时间、静态路线示意和雨天替代；离线地图素材与照片许可需单独验证。

### P2 — 扩展与运营

9. 在三城真实路线质量达标后，扩展城市与 10 天以上、多次跨城的分段规划；按景点数据覆盖度开放能力。
10. 建立真实用户评测：英文可理解性、地点/入口正确率、交通时间偏差、预约冲突检出率、路线修改成功率，以及出发前实际使用情况。付费价值用真实预览和购买测试验证。

## 6. 最近一个开发迭代的具体交付

建议先做 **“可执行的一天”**，不同时改动所有系统：

1. 选定一个带酒店、固定预约和两处景点的案例，核对官方入口与预约规则。
2. 增加来源和事实状态字段，并在景点卡/时间线呈现。
3. 针对该案例完成入口导航、预约冲突、步行与排队缓冲、英文/中文地点卡。
4. 用手机和桌面实际走通“提需求 → 看地图 → 改安排 → 查待确认事项”；记录地图、对话、卡片之间的不一致。

完成这条闭环后，再接入月度拥挤趋势试点和后端版本保存。这样每项新增数据都会实际改变行程决策，而不只是在页面上多放一张图。
