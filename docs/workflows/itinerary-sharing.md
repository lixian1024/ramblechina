# Revocable itinerary sharing

Only a signed-in owner can publish a saved itinerary. The owner opens Share itinerary, checks the exact public preview, and confirms that anyone with the link can read its cities, dates and itinerary until revocation. Publication reads the saved database version; unsaved planner edits are excluded.

Each explicit publication generates 32 cryptographically random bytes and replaces the previous capability. Only a SHA-256 hash is stored. POST returns the link once; GET deliberately never returns it. A lost response can be recovered by publishing a new link or revoking. Republish invalidates every previous link for the trip. DELETE is idempotent for an owned trip. Ordinary edits/saves do not update an existing published snapshot.

PostgreSQL constructs the public snapshot, including for direct authenticated Data API mutations. Its whitelist contains cities, valid-format dates, ordered stop names, durations and fixed uncertainty summaries. Personalized reasons (`why`/`reason`), trip titles/summaries, conversations, hotel/address/booking fields, maps, provider identifiers/photos/content, weather and temporary data are omitted. Neither reasons nor original free-prose warning strings are copied into the public snapshot: partial names and hotel aliases cannot be reliably anonymized with exact-text filters.

The private save retains app-produced warning strings. Publication maps each warning to a fixed opening/closure, reservation/access, location, timing/conflict, weather, transport or source summary; unmatched warnings produce a generic warning directing the owner to the private plan. This preserves uncertainty without publishing embedded names, booking notes or hotel aliases. Public summaries are deliberately less detailed; publication does not revalidate venue facts.

City and stop names remain free-text labels intended for disclosure. Known profile/email/hotel/booking/address matches and obvious sensitive patterns are omitted conservatively, but these filters cannot anonymize arbitrary names or aliases in those labels. The owner must review the exact preview and remove private details before publishing. The page shows publication time and uncertainty, performs no paid lookup, retains missing dates/empty days explicitly, and does not manufacture a route.

`ramble_trip_shares` has owner RLS and no anonymous table grants. Authenticated callers cannot write snapshot/publication-date columns. A security-invoker trigger reads only their owned saved trip and builds the whitelist. The sole anonymous RPC is `ramble_read_trip_share(capability)`: a narrow security-definer lookup validates a 43-character random capability and returns only sanitized snapshot and publication date. It returns null for unknown/revoked/malformed capabilities. Database or configuration failure is reported separately from a missing link. No service-role key is required.

API: GET `/api/trips/[uuid]/share` returns `{published,publishedAt?,preview}`; POST JSON `{confirmed:true,locale:"en"|"zh"}` returns 201 `{path,publishedAt}`; DELETE returns `{published:false}`. Owner requests use private/no-store responses; POST and DELETE require same origin. Public pages are dynamic/no-store, noindex/nofollow and no-referrer, and never enter the sitemap. Analytics must omit token-bearing routes and referring URLs.

Migration `supabase/migrations/20261023031821_ramble_trip_shares.sql` is prepared and repeatable, and was tested in isolated PGlite. It was applied to the live project on2026-10-23 after controlled integration verification. Actual owner publication and separate anonymous access/revocation remain release gates; two-owner isolation is currently verified in isolated PostgreSQL, not two real accounts. Run `node --import tsx scripts/verify-sharing.ts`, `node --import tsx scripts/verify-sharing-ui.ts` and `node --import tsx scripts/verify-sharing-api.ts` for controlled PostgreSQL/SDK and component checks. These are not live product evidence or travel-quality approval.


Privacy regression: `verify-sharing.ts` calls the production `safeSnapshot`, saves its result into PostgreSQL, then uses the production publication store and anonymous RPC. The case includes profile “Jane Smith”, hotel “The Middle House”, and the reason “A relaxed walk for Jane and her son Tim, before returning to Middle House.” Public output must omit that prose and those private references while retaining city/date/order/duration and fixed source, opening, reservation and timing warnings. This is controlled regression evidence, not a guarantee that arbitrary stop labels contain no personal data.
