# Plan a Trip: Travel Assistant and Route Concierge

Updated 2026-10-07 in `china-unfold`.

## Current page

The English planner is available at `/en/plan`, and the Simplified Chinese planner at `/zh/plan`. The language switch keeps travellers on this page when switching between English and Chinese. The Chinese edition uses Chinese interface text, assistant replies, itinerary descriptions, scheduling checks, weather/transport warnings and retry messages. Each language keeps a separate browser draft; existing English storage is preserved. The Chinese page always uses the Chinese AMap basemap, including after the English map permission is enabled. The legacy `?view=classic` editor remains available only on the English page.

`/[locale]/plan` first classifies each new question. Requests to create or change a day-by-day route go to Route Concierge. Travel questions that only ask for information, destination ideas or comparisons go to Travel Assistant, which answers with Qwen web search and source links without changing the saved itinerary or map. Unrelated questions receive a short, friendly travel-scope reply. If a traveller later asks to add recommended sights to the route, the Route Concierge sees the relevant Travel Assistant exchange so references such as “the second place” remain usable.

For a new plan or revision, travellers describe their dates, hotels, companions, pace and existing tickets in natural language. Route Concierge first makes a forced Qwen web-search call through Model Studio's native DashScope API, retaining the search brief and source links. A second model call turns that fresh research and the traveller's constraints into a structured draft. The service then checks place matches, route estimates and date-specific weather with AMap before returning a day-by-day plan. If live research yields no usable sources, planning stops with a retryable error instead of silently drafting from model memory. On desktop, conversation and itinerary are on the left, and the map is on the right in equal-width columns. The conversation follows page scrolling, while the map stays visible beside it. Place details below the map have their own scroll area. On phones, tabs switch between the two views. All days are now shown together on the left, with a separate intercity transport card between cities. Stop cards show consistent day.stop numbers, Chinese and English names, Mandarin pinyin, category, suggested visit duration, sourced admission references and recommended visit windows. Missing details in older drafts have explicit placeholders and an assistant enrichment action. Selecting a stop shows its map pin and photo/details on the right. Conversation history is collapsible. Contextual earlier/later/replace/remove, add-stop, refine-day and change-transport buttons prepare a specific conversational request in the composer; no itinerary changes until the traveller sends it. Fixed bookings disable reorder/replace shortcuts; their removal request explicitly cancels only the itinerary booking, not the actual ticket. The last successful revision remains undoable. The composer stays accessible while browsing. A follow-up request revises the plan, and the interactive map updates with it.

Booked stops from an existing draft retain their recorded time during ordinary revisions. The server checks whether fixed times collide with preceding stops, estimated travel or a same-day cross-city connection. Cross-city days get a separate origin-to-destination AMap estimate, an optional driving alternative and a visible planning buffer. The itinerary, messages and latest plan are stored in browser local storage, with an undo action for the last successful change.

The interactive map starts in **Whole trip** mode and can switch to any day. It fits all matched places in the current view, supports drag and zoom, and offers a fit-all button. AMap route geometry is drawn as a solid line when supplied by the directions API. Rail segments, overnight links and routes without geometry are dashed schematic connections. Previously saved plans without geometry refresh their checked legs in the background. Map markers, daily timelines and place cards all use the same day.stop numeric labels (1.1, 1.2, 2.1), which remain unchanged when switching between whole-trip and daily views. Clicking a marker selects that day's stop. The composer stays accessible at the bottom while browsing the conversation. On phones, the conversation retains its own scroll area and view tabs switch to the map.

## Local configuration

- `AMAMP_API_KEY`: existing **AMap Web Service** key in `.env.local`. It stays server-side. The fallback name `AMAP_WEB_SERVICE_KEY` also works. A JS API key cannot replace this Web Service key.
- `AMAP_JS_API_KEY`: Web platform JS API key. The server passes this browser key to the map component.
- `AMAP_JS_API_SECRET`: JS API security code. It remains server-side and is attached by the local `/_AMapService` proxy. The key also needs AMap's multilingual-map permission for English labels.
- `AMAP_JS_ENGLISH_ENABLED=true`: enable the AMap English basemap **after** AMap grants multilingual-map permission. The current JS key returned `INSUFFICIENT_PRIVILEGES` in a local English-map check, so this flag is deliberately unset.
- `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`: retained for the legacy Google component; the current Plan page does not load Google Maps or fall back to it.
- Set `DASHSCOPE_API_KEY` to a pay-as-you-go Model Studio key and `DASHSCOPE_BASE_URL` to the matching workspace's `/compatible-mode/v1` URL. `QWEN_MODEL` defaults to `qwen-plus`; the current local configuration uses `qwen3.6-plus` for structured planning. Every plan requires a Qwen model and this base URL so that forced web research and returned source links work. The search pass uses text-only `qwen-plus` (override with `QWEN_SEARCH_MODEL`) on the same host's native `/api/v1` endpoint with `enable_search`, `forced_search`, and `enable_source`. The configured `qwen3.6-plus` is a multimodal model and cannot use that native text-generation endpoint for search. The JSON planning pass disables thinking mode because JSON Object mode requires it. `TRIP_LLM_API_KEY` and `TRIP_LLM_MODEL` can override key and model only when they still point to a Qwen Model Studio configuration.
- Alibaba Cloud's Token Plan and Coding Plan endpoints/keys are restricted to interactive coding tools. The travel app backend rejects them before making a model call. Use a standard Model Studio pay-as-you-go API key and matching regional base URL; see [Alibaba Cloud endpoint types](https://help.aliyun.com/en/model-studio/base-url).
- Restart the dev server after editing `.env.local`. No model key is checked into this repository. A missing key gives an explicit in-page error.

## Data and limits

The page uses AMap v5 POI search, v5 walking/driving/transit route estimates, and v3 weather forecasts. AMap JS API 2.0 renders the interactive basemap in Chinese by default. Its GCJ-02 coordinates directly align with AMap Web Service places and routes, so the page renders those coordinates without conversion. After multilingual-map access is granted, set `AMAP_JS_ENGLISH_ENABLED=true` and restart the app to use `languageCode: 'en'`. The JS API security code stays behind a same-origin server proxy. The page stays on AMap while multilingual access is pending; loading failures show a retry action rather than switching providers. The existing static AMap proxy remains for older consumers.

Weather appears only for dates returned by AMap. AMap route duration is an estimate at lookup time, not a future traffic forecast or a confirmed service. Cross-city calculations use matched hotel locations when available; otherwise a matched stop is used and the itinerary says what needs confirmation. Intercity rail/flight/road modes from the model are suggestions, shown separately from AMap lookup estimates; they are not booked or confirmed services. Admission text is accepted only with a supporting URL from the current research source list and displayed as a linked price reference, not a verified ticket quote. Unknown admission remains “to check”; even free admission needs a cited reference. Visit durations and best-time windows are planning recommendations. Train or flight numbers, seat availability, admission tickets, exact entrances and venue opening hours are not confirmed by this feature. Missing locations or routes remain visibly unverified.

The model proposes the itinerary using live search; it does not create invented AMap facts. The page shows the research brief and its source links, but a returned search result is not by itself proof of any specific booking or opening rule. All incoming model fields are bounded and normalized before matching. POI matching uses AMap categories so a sight is not silently replaced by a transit station, and removes duplicate hotel/visit stops; unresolved places remain marked for confirmation. User conversation, previous drafts, and retrieved pages are treated as trip data. The UI shows actual lookup stages, not model-internal reasoning.

## Routes and verification

- `src/app/api/trip-concierge/route.ts`: validates the request, selects an agent and streams intent, answer or plan events.
- `src/app/api/trip-route-geometry/route.ts`: bounded refresh of route geometry for older browser-saved plans.
- `src/app/%5FAMapService/[...path]/route.ts`: same-origin AMap JS API security proxy; the encoded folder creates the `/_AMapService` URL required by AMap.
- `src/app/api/trip-map/route.ts`: proxies AMap static map images without exposing the key.
- `src/lib/travel/concierge.ts`: question classification, researched travel answers, model draft, booked-stop preservation, schedule and consistency checks.
- `src/lib/travel/concierge-amap.ts`: AMap service requests and short-lived server cache.
- `src/components/travel/AmapConciergeJourneyMap.tsx`: AMap Chinese/English basemap, whole-trip and day route layers, zoom controls and marker selection.
- `src/components/travel/GoogleConciergeJourneyMap.tsx`: legacy Google implementation, not loaded by the current Plan page.
- `src/components/travel/ConciergeJourneyMap.tsx`: AMap language selection, missing-key status and loading retry.
- `src/components/travel/Planner.tsx`: conversation, map and contextual request composer.
- `src/components/travel/ItineraryOverview.tsx`: all-day itinerary, rich stop cards, separate intercity cards and conversational editing shortcuts.
- `src/lib/travel/itinerary-display.ts`: shared weather, duration, transport and category display helpers.
- `scripts/verify-concierge.ts`: deterministic mock coverage of model output, place/route/weather lookup, booking preservation and cross-city transfer.
- `scripts/verify-trip-routing.ts`: deterministic mock coverage of travel advice, unrelated questions, route changes and follow-up context.

Run `npx tsx scripts/verify-trip-routing.ts`, `npx tsx scripts/verify-concierge.ts`, `npx eslint` on the new files, and `npm run build`. The original rule-based form planner remains at `/[locale]/plan?view=classic` for reference; it is separate from Route Concierge state.
